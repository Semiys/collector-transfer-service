# Гостевая проверка заказа

## Что добавлено

Страница `/order` показывает сумму, состояние оплаты, состояние обработки и время обновления **своего** заказа по полному коду доступа. Регистрация и административная сессия не нужны. На `/automatic` есть кнопка «Проверить заказ».

Публичное оформление, оплата, запуск ИИ и получение оплаченного ZIP ещё закрыты. **Коды посетителям пока не выдаются:** они появятся в сценарии оформления после подключения оплаты. Черновик в админке не выдаёт гостевой код и не становится оплаченным от проверки статуса. Для проверки успешного доступа автоматические тесты создают отдельные вымышленные заказы.

## Код доступа

Формат: `CT1.<номер заказа UUID>.<случайный токен из 64 hex-символов>`. Внутренний `newOrderAccessToken()` создаёт токен с 256 битами случайности; `formatOrderAccess()` собирает код. `parseOrderAccess()` проверяет версию и структуру, принимает переносы строк/пробелы при копировании и нормализует регистр. Сам номер заказа не даёт доступа.

Код является секретом доступа к заказу. Сервер хранит только SHA-256 хеш токена; публичный ответ не содержит токен, хеш, идентификаторы платежей/возвратов или диагностические данные ИИ. Неверный токен и неизвестный номер получают одинаковое сообщение 404. Код нужно сохранить у себя и не передавать другим людям. Если код утрачен, автоматического восстановления по имени/коллекции нет: сайт не хранит такие сведения и не имеет гостевых аккаунтов.

Код отправляется только JSON-телом `POST /api/orders/status`, не в URL/QR/query/hash. Скрипт не пишет его в localStorage, sessionStorage, cookies или журналы. Поле по умолчанию скрыто; «Показать код» временно раскрывает его. «Очистить» отменяет текущий запрос, убирает код и результат; ответ отменённого запроса не восстанавливает их. При обновлении/уходе со страницы поле очищается. `autocomplete="off"` просит браузер не сохранять значение, но расширения и менеджеры паролей контролируются самим пользователем.

Страница и API отдают `Cache-Control: no-store` и `Referrer-Policy: no-referrer`. CSP страницы ограничивает скрипты/подключения своим источником и запрещает встраивание в iframe. В production обязательны HTTPS и отключение записи тел запросов на уровне прокси, APM и инфраструктуры.

## Восстановление после перезапуска

При сохранённом `DATA_DIR/orders.json` тот же код открывает статус после перезапуска сервиса, в другом браузере и на другом устройстве. Состояние оплаты сохраняется; незавершённая/готовая обработка после перезапуска становится прерванной. **Исходник, модели, исправления и ZIP не восстанавливаются:** они остаются только в RAM. При будущем повторе нужен исходник и новый номер попытки.

Этот механизм не восстанавливает потерянный том или повреждённую/удалённую запись заказа. Ограничения одного процесса и резервирования только метаданных описаны в `ORDERS_AND_PAYMENTS.md`.

## API и ограничения

- `GET /api/orders/config`: доступность проверки; создание, оплата и запуск всегда `false` на текущем этапе.
- `POST /api/orders/status`: только `{ "code": "..." }`, тело до 2 КиБ. Дополнительные поля с коллекцией/файлом/ценой отвергаются.
- До 20 проверок в минуту на IP, не более двух одновременных HTTP-проверок. Для 429/занятости возвращается `Retry-After`. Счётчики находятся в RAM; доверенный прокси настраивается отдельно.
- CAPTCHA для просмотра метаданных не нужна: запрос не загружает коллекцию, не вызывает ИИ, не создаёт ZIP и не меняет оплату. Ресурсоёмкие действия сохраняют собственные проверки.
- Нет публичных маршрутов создания, оплаты, подтверждения или запуска. Гостевой код не даёт доступ к административным маршрутам.
- Неожиданный отказ хранилища возвращает безопасный 503; повреждённый файл не очищается и не перезаписывается.

## Проверка

`test/guest-orders.test.js` содержит семь проверок формата, чужого доступа, восстановления статуса, публичного ответа, закрытых действий, ошибок хранения и лимитов. Оплата только вымышленная, внешние ИИ/CAPTCHA не вызываются. На этапе гостевого статуса прошли 83/83; после внутренней выдачи ZIP текущий полный комплект — **97/97** на установленном Node.js 22.14.0. Docker с целевым Node.js 24 проверяется на втором ПК.

Интерфейс проверен локально с отдельным вымышленным заказом, в двух темах и на ширине 320 px. Ручные сценарии — раздел L `MANUAL_TEST_CHECKLIST.md`; успешный гостевой доступ на рабочем сайте можно проверить после появления выдачи кодов. Не пытайтесь использовать админ-код или хеш из `orders.json` вместо гостевого кода.
