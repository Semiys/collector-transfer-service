# Учёт заказов перед подключением оплаты

## Что работает сейчас

В админ-панели появился раздел **«Заказы»**. Администратор может создать неоплаченный черновик на **149 ₽**, обновить список и удалить черновик, ещё не связанный с платежом. Создание черновика не вызывает ИИ, не загружает коллекцию и не списывает деньги. На странице `/automatic` гостевая обработка и оплата остаются отключёнными.

Заказы хранятся в `DATA_DIR/orders.json` (в Docker — `/app/data/orders.json` в существующем томе). Это отдельные служебные записи: случайные номера заказов и запросов, хеш ключа доступа, сумма, валюта, идентификаторы платёжного сервиса, статусы и время операций. **Имена файлов, текст, модели, фото, ответы ИИ и ZIP туда не записываются.** Настройки `.env` для этого блока не меняются; нужен уже настроенный код администратора.

Ключ доступа к заказу хранится только в виде SHA-256 хеша. Административный список не отдаёт ни его, ни идентификаторы платежей/возвратов. Для административных черновиков ключ выводится на сервере из админ-кода и номера запроса; браузер его не получает. Смена админ-кода изменяет этот механизм повтора черновиков, но не удаляет существующие записи. Это не готовый механизм восстановления гостевого заказа.

Страница `/order` теперь проверяет сумму и статус по полному гостевому коду без входа; сохранённый код работает после перезапуска при сохранённом томе. Выдача кодов при оформлении ещё не подключена. Административные черновики не выдают их посетителям. Подробности — [GUEST_ORDER_ACCESS.md](GUEST_ORDER_ACCESS.md).

## Серверная основа будущей оплаты

`src/orders/store.js` содержит переходы состояний, которые проверяются автоматическими тестами с вымышленными платежами:

1. Создать заказ: сумму 14900 копеек и валюту RUB задаёт сервер. Повтор того же номера запроса с тем же ключом доступа возвращает прежний заказ.
2. Связать заказ с уникальным платежом. Другой заказ не может использовать тот же платёж.
3. Подтвердить платёж: номер, платёжный сервис, сумма и валюта должны совпасть. Только оплаченный заказ разрешает начать обработку.
4. Начать попытку: повтор одного запроса возвращает прежнюю попытку; одновременная новая попытка запрещена. Вызывающий код обязан запускать рабочую обработку **только при `started: true`**.
5. Отметить готовность, завершение или причину неудачи. Перед разрешением повтора вызывающий код должен остановить прежнюю работу и дождаться её остановки.
6. После перезапуска незавершённая/готовая попытка становится прерванной. Подтверждённая оплата сохраняется; исходник и результат из RAM восстановить нельзя. Для новой попытки нужен новый номер запроса и повторная загрузка исходника.
7. Зафиксировать запрос полного возврата и затем его подтверждение. Возврат блокирует новые попытки; запоздалое повторное подтверждение оплаты не отменяет возврат.

В пилотной основе заложено **три попытки на заказ**, включая прерванные. Это техническая настройка, а не опубликованное коммерческое условие. Перед реальной оплатой нужно согласовать правила повторов, потери результата и возвратов. По достижении лимита заказ остаётся оплаченным и требует решения о возврате; деньги автоматически не возвращаются.

**Подтверждающие методы — внутренний API, а не проверка подлинности платежа.** Будущий адаптер платёжного сервиса должен сначала проверить уведомление допустимым для него способом и получить актуальный подтверждённый статус платежа. Браузерный ответ и непроверенное уведомление не могут считаться оплатой. Сейчас HTTP-маршрутов «пометить оплаченным» или «подтвердить возврат» нет даже у администратора.

## Чего ещё нет

- Платёжного сервиса, эквайринга, платёжной ссылки, реальных уведомлений и возврата денег.
- Гостевого создания заказа, выдачи кода при оформлении и восстановления утраченного кода. Проверка статуса по уже имеющемуся коду работает.
- Публичного запуска гостевых оплаченных заданий с CAPTCHA и согласиями. Внутренняя связь оплаченного заказа с очередью уже добавлена — см. `ORDER_PROCESSING.md`.
- Гостевого интерфейса ZIP и утверждённых коммерческих правил его получения/повторов. Внутренний адаптер `ORDER_DELIVERY.md` уже отделяет сборку от явного подтверждения сохранения пользователем; ответ сервера сам по себе не доказывает, что файл сохранён.

Поэтому текущие тесты подтверждают серверные переходы и защиту API, **но не полный платный путь**. Результаты коллекций по-прежнему остаются только в оперативной памяти.

## Хранение и ограничения

Запись операций выполняется по очереди в одном процессе. Изменённый файл записывается во временный файл с синхронизацией, затем заменяется переименованием. Повторные подтверждения не создают дополнительных записей. Повреждённый JSON, неизвестные поля и несогласованные состояния останавливают операции с ответом 503; файл автоматически не очищается и не заменяется.

Эта версия рассчитана на **один процесс/один контейнер**, максимум 10000 заказов, файл до 20 МБ. Два контейнера с общим томом и несколько Node-процессов использовать нельзя: межпроцессной блокировки нет. Нет гарантии против потери данных при отказе диска или аварийном отключении питания. Перед публичной оплатой нужны надёжное хранилище, резервирование метаданных и проверка восстановления. Резервировать содержимое коллекций запрещено; резервная копия служебных записей заказов допустима отдельно.

При испорченном файле остановите приём новых заказов и восстановите проверенную резервную копию метаданных. Не удаляйте `orders.json` для «исправления»: так можно потерять сведения об оплаченных заказах.

## Проверка на втором ПК

1. Обновить исходники и пересобрать контейнер по `SECOND_COMPUTER_SETUP.md`.
2. Войти в `/admin`, выбрать «Заказы», создать черновик. Записать его полный номер.
3. Обновить страницу, затем перезапустить контейнер. После нового входа номер и статус «Ожидает оплаты» должны сохраниться, попыток — 0.
4. Удалить этот неоплаченный черновик: список обновляется. Удаление настоящих связанных/оплаченных заказов этим действием запрещено.
5. Проверить обе темы и мобильную ширину. На `/automatic` деньги по-прежнему не принимаются.

Накопительные сценарии — раздел J в `MANUAL_TEST_CHECKLIST.md`. Автоматические проверки — `test/orders.test.js` и `test/orders-http.test.js`; настоящие платежи они не используют.

Связь заказа с очередью также проверяется в `test/order-processing.test.js`. Распознавание не помечает заказ завершённым и не подменяет выдачу ZIP. Новые публичные оплаченные действия ещё отключены.
